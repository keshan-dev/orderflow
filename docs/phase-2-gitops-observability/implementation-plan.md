# Phase 2 Implementation Plan

10 milestones, M0 to M9. Do them in order. Each milestone has a **goal**, **tasks**, **how to test**, and **done when**. Do not start the next milestone until the current one passes its test.

Commands are examples. Names generated by tools (like the Envoy Service name) may differ on your machine, so check with `kubectl get`.

New folders this phase adds to the [repository](../common/02-architecture.md#14-repository-layout):

```
deploy/kind/            kind cluster config, local registry script
deploy/helm/            library chart, 5 service charts, platform values
deploy/argocd/          root app, apps, ApplicationSet
deploy/observability/   dashboards (JSON), alert rules, Collector config
loadtest/               k6 scripts
chaos/                  Chaos Mesh experiments and incident write-ups
.github/workflows/      CI
```

## M0: Cluster up

**Goal:** a 3 node kind cluster with a local registry, metrics-server and Envoy Gateway.

Tasks:
- [ ] Give Docker Desktop a memory limit in `.wslconfig` that leaves room for Windows.
- [ ] Write `deploy/kind/kind-config.yaml`:
  ```yaml
  kind: Cluster
  apiVersion: kind.x-k8s.io/v1alpha4
  name: orderflow
  nodes:
    - role: control-plane
    - role: worker
    - role: worker
  ```
- [ ] Create the cluster: `kind create cluster --config deploy/kind/kind-config.yaml`
- [ ] Set up a local registry next to kind, following the kind "Local Registry" page. (The script there is bash: run it in Git Bash or WSL.)
- [ ] Install metrics-server (kind needs the flag for self signed kubelet certificates; see its README).
- [ ] Install Envoy Gateway with Helm. Create a `Gateway` named `orderflow`.
- [ ] Install cert-manager into the `cert-manager` namespace (Phase 3 needs it for webhook certificates).
- [ ] Create namespaces `dev`, `staging`, `prod`, `data`, `kafka`, `monitoring`.
- [ ] Write the versions you installed into `PLAN.md`.

How to test:
```bash
kubectl get nodes                      # 3 nodes, all Ready
kubectl top nodes                      # numbers appear (metrics-server works)
kubectl get gateway -A                 # orderflow gateway is Programmed
kubectl get pods -n cert-manager       # all Running
```

Done when: all 3 commands give the expected result, and you can delete and recreate the cluster in a few commands.

## M1: Data layer

**Goal:** PostgreSQL, Kafka, Debezium, RabbitMQ, OpenSearch, Redis and S3 storage run in the shared `data` and `kafka` namespaces, managed by operators.

Tasks:
- [ ] Install the operators: CloudNativePG and the RabbitMQ Cluster Operator in their default namespaces, Strimzi watching the `kafka` namespace.
- [ ] PostgreSQL: a CloudNativePG `Cluster` with 1 instance in `data`. Create `orders_db`, `inventory_db`, `payments_db`. Make sure logical replication is on for Debezium.
- [ ] Kafka: Strimzi `Kafka` + `KafkaNodePool` in KRaft mode, 1 broker, in `kafka`. Turn on the Kafka Exporter (you need it for consumer lag metrics in M6).
- [ ] Topics as Strimzi `KafkaTopic` resources (the only way topics are created): `orders.events`, `inventory.events`, `payments.events`, and their `.retry` and `.dlq` topics. Choose a partition count and write it in the decision log.
- [ ] Debezium: Strimzi `KafkaConnect` with a `build` section that adds the Debezium PostgreSQL plugin and pushes to your local registry. 3 `KafkaConnector` resources, 1 per outbox table, with the Outbox Event Router.
- [ ] RabbitMQ: a `RabbitmqCluster` with 1 replica in `data`.
- [ ] OpenSearch: official Helm chart, single node, security plugin off for local dev only. Raise `vm.max_map_count` on the host first.
- [ ] Redis: `StatefulSet` with the official `redis` image and a volume.
- [ ] S3: MinIO with the bucket `orderflow-invoices`. MinIO community edition changed its distribution in 2025, so first check that a prebuilt image exists for the version you want to pin. If not, use an S3 compatible fallback such as SeaweedFS or Garage (follow its own docs). Write the choice in the decision log.
- [ ] Store all of this as YAML and values files in `deploy/helm/platform/`. In M4, Argo CD will take it over.

How to test:
```bash
kubectl get pods -n data                        # all Running and Ready
kubectl get pods -n kafka                       # all Running and Ready
kubectl get cluster -n data                     # CloudNativePG cluster healthy
kubectl get kafka,kafkatopic,kafkaconnector -n kafka
kubectl get rabbitmqcluster -n data
```
Then insert 1 test row into the `outbox` table of `orders_db` and check it appears on `orders.events` (with a Kafka console consumer pod or Kafka UI).

Done when: an outbox row reaches Kafka, and every store survives a pod delete (`kubectl delete pod ...`) without losing data.

## M2: Helm charts

**Goal:** the library chart `orderflow-lib` and 5 small service charts.

Tasks:
- [ ] Create `deploy/helm/orderflow-lib` with `type: library` in `Chart.yaml`.
- [ ] Templates: Deployment (with a switch to render an Argo `Rollout` later), Service, HTTPRoute, HPA, ServiceMonitor, PDB.
- [ ] Every pod gets: resource requests and limits, liveness probe on `/healthz`, readiness probe on `/readyz`, environment from a ConfigMap and from Secrets.
- [ ] Standard labels on every object, including `app.kubernetes.io/component: api` for order, inventory and payment services and `app.kubernetes.io/component: worker` for notification-worker and search-indexer.
- [ ] Generic env vars only: `DATABASE_URL`, `REDIS_URL`, `KAFKA_BOOTSTRAP_SERVERS`, `RABBITMQ_URL`, `S3_BUCKET`, `OPENSEARCH_URL`. They point at the stores in `data` and `kafka` with full DNS names (for example `redis.data.svc.cluster.local`).
- [ ] 5 service charts. Workers have no Service or HTTPRoute.
- [ ] `values.yaml` plus `values-dev.yaml`, `values-staging.yaml`, `values-prod.yaml`. Prod has more replicas and a PDB.
- [ ] HTTPRoutes: `/api/orders` to `order-service` port 8001, `/api/products` to `inventory-service` port 8002.

How to test:
```bash
helm lint deploy/helm/order-service
helm template order-service deploy/helm/order-service -f deploy/helm/order-service/values-dev.yaml
```
Read the rendered YAML. Check the probes, limits and labels are there.

Done when: all 5 charts lint cleanly and render the objects you expect for each environment.

## M3: Manual install (once, to learn)

**Goal:** the full order flow works on Kubernetes, installed by hand 1 time before GitOps takes over.

Tasks:
- [ ] Build the 5 images and load them into kind: `kind load docker-image order-service:dev --name orderflow` (or push to the local registry).
- [ ] `helm install` each service into `dev` with `values-dev.yaml`.
- [ ] Run the database migrations (an init container or a Kubernetes `Job`).
- [ ] Port forward the Envoy Service to local port 8080:
  ```bash
  kubectl get svc -n envoy-gateway-system          # find the Envoy Service name
  kubectl port-forward -n envoy-gateway-system svc/<envoy-service> 8080:80
  ```

How to test: place an order through `http://localhost:8080/api/orders` with an `Idempotency-Key` header, the same request as in Phase 1. Check:
- the order reaches `CONFIRMED`,
- the email is in Mailpit,
- the PDF is in the `orderflow-invoices` bucket,
- `GET /api/orders/search?q=` finds it.

Then test a failure case from Phase 1 (out of stock, payment failure) and check it ends in `CANCELLED` with stock released.

Done when: the full happy path and both failure paths pass on Kubernetes. Then `helm uninstall` everything; Argo CD installs it from now on.

## M4: Argo CD

**Goal:** the whole cluster content comes from Git.

Tasks:
- [ ] Install Argo CD into `argocd` (Getting Started page).
- [ ] Write `deploy/argocd/root-app.yaml` (app of apps) pointing at `deploy/argocd/apps/`.
- [ ] `apps/operators.yaml` (sync wave 0), `apps/platform.yaml` (wave 1), `apps/monitoring.yaml` (wave 1, filled in M6), `apps/services-appset.yaml` (wave 2).
- [ ] The ApplicationSet uses a matrix generator: services x environments. Each environment has an `enabled` flag. Only `dev` is enabled by default.
- [ ] `dev`: automated sync with prune and self heal. `prod`: manual sync.
- [ ] If the repository is private, Argo CD needs read access. Create that credential by hand in the cluster. Never commit it.
- [ ] Apply the root app 1 time by hand: `kubectl apply -f deploy/argocd/root-app.yaml`. That is the last manual apply.

How to test:
```bash
kubectl get applications -n argocd               # all Synced and Healthy
kubectl scale deployment order-service -n dev --replicas=5
kubectl get deployment order-service -n dev -w   # self heal puts it back
```
Change `replicaCount` in `values-dev.yaml`, push, and watch Argo CD apply it. Then roll back to the previous commit from the Argo CD UI or by reverting the commit.

Done when: you can delete the cluster, recreate it, install Argo CD, apply the root app, and everything comes back by itself.

## M5: CI pipeline

**Goal:** a push produces a tested, scanned, signed image and a tag bump pull request.

Before you start: check the GitHub Actions minutes and package storage included in the plan of the account that owns the repo. Public repos and private repos have different limits. If the work would need more than what is included, or any paid add on, follow the spend rule first.

Tasks:
- [ ] `.github/workflows/ci.yaml`, run on pull requests and on pushes to `main`. Only build services whose folder changed (path filters).
- [ ] Job `test`: `ruff check`, `pytest` for Python services, `go test ./...` for payment-service.
- [ ] Job `image`: `docker build`, tag with the git commit SHA, Trivy scan with `CRITICAL` severity and a failing exit code, push to GHCR, sign with cosign keyless (needs `id-token: write`).
- [ ] Job `bump`: on `main` only, change the image tag in `values-dev.yaml` and open a pull request.
- [ ] Give each job the smallest `permissions` it needs. Pin third party actions to a full commit SHA.
- [ ] If the GHCR images are private, create an image pull Secret in the cluster by hand. Never commit it.

Illustrative shape:
```yaml
permissions:
  contents: read
jobs:
  image:
    permissions:
      contents: read
      packages: write
      id-token: write
    steps:
      # checkout, build, trivy scan (fail on CRITICAL), push, cosign sign
```

How to test:
- Open a PR with a failing test: CI goes red.
- Add a package with a known critical CVE on a test branch: the Trivy step fails.
- Merge a normal change: a signed image appears in GHCR, a tag bump PR opens, and after you merge it Argo CD deploys it.
- Verify the signature with `cosign verify`.

Done when: 1 commit goes from push to running pod in `dev` with no manual command except the 2 merges.

## M6: Observability

**Goal:** metrics, logs and traces for every service, linked together in Grafana.

Tasks:
- [ ] Through `apps/monitoring.yaml`: kube-prometheus-stack, Loki, Grafana Alloy, Jaeger, OpenTelemetry Collector. Short retention to save RAM.
- [ ] Turn on exemplar storage in Prometheus.
- [ ] Metrics: each service exposes `/metrics` with request count, error count and a latency histogram (labels: `service`, `route`, `method`, `status`). Workers expose processed, failed and retried message counters. The library chart's ServiceMonitor makes Prometheus scrape them.
- [ ] Traces, Python: OpenTelemetry instrumentation for FastAPI, httpx, SQLAlchemy and Redis. Export with OTLP to the Collector.
- [ ] Traces, Go: `otelhttp` for payment-service, plus manual spans around the fake provider call.
- [ ] Kafka trace context: the `traceparent` column already exists in every `outbox` table from Phase 1 (add it with an Alembic migration if you skipped it). Fill it when writing the event, and configure the Debezium Outbox Event Router to place it as a Kafka header. Consumers extract it and start their span as a child.
- [ ] RabbitMQ trace context: order-service injects `traceparent` into the message headers; notification-worker extracts it.
- [ ] Logs: JSON to stdout with `trace_id` and `span_id` on every line. Alloy ships them to Loki.
- [ ] Grafana: data sources for Prometheus, Loki, Jaeger and OpenSearch (Phase 4 dashboards use the OpenSearch one). Set up exemplars (metric to trace), trace to logs (Jaeger to Loki by `trace_id`), and derived fields (log to trace).
- [ ] Dashboards in `deploy/observability/dashboards/`: 1 RED dashboard per HTTP service (rate, errors, duration), 1 for Kafka consumer lag, 1 for RabbitMQ queue depth. Load them through Grafana provisioning, so they live in Git.

How to test:
- Place 1 order. In Jaeger, find 1 trace that contains spans from order-service, inventory-service, payment-service, search-indexer and notification-worker.
- Copy its `trace_id`. In Grafana Explore with Loki: `{namespace="dev"} | json | trace_id="<id>"` shows the log lines of all services.
- On the latency panel, click an exemplar dot and land on a trace.
- Stop `search-indexer` (scale to 0), place orders, and watch consumer lag grow on the dashboard.

Done when: 1 order is 1 trace across HTTP, Kafka and RabbitMQ, and you can move between metrics, traces and logs with clicks only.

## M7: SLOs and alerts

**Goal:** SLOs for `POST /api/orders` with burn rate alerts that reach a safe local inbox.

Tasks:
- [ ] Write the SLOs in `deploy/observability/slo.md`: availability (share of non 5xx responses) and latency (share of requests faster than a threshold). Pick the targets and the threshold after measuring normal latency in M6. Write the reasons in the decision log.
- [ ] Optional SLI: time from `PENDING` to `CONFIRMED`. `POST /api/orders` returns `202` early, so this measures what the customer really waits for.
- [ ] `PrometheusRule` with recording rules for the error ratio over several windows, and multi window burn rate alerts as described in the SRE Workbook "Alerting on SLOs" chapter. For demos, use shorter windows and note in the file that real ones are longer.
- [ ] Add alerts for: Kafka consumer lag too high, messages in any `.dlq` queue or topic, pod restarting often.
- [ ] Alertmanager receivers: Mailpit (email) inside the cluster, or a tiny local webhook receiver that logs what it gets. No real email, Slack or SMS.
- [ ] Note the in-cluster address of the Alertmanager Service in `monitoring` (`kubectl get svc -n monitoring`) in `PLAN.md`. Phase 4's detection-service sends alerts to it.
- [ ] Add a dev only fault switch to order-service: the env var `FAULT_ERROR_RATE` (a number from 0 to 1, default 0) makes that share of requests return 500. It is used here and in M8. Never set it in `values-prod.yaml`.

How to test: turn on the fault switch in `values-dev.yaml`, run a small k6 load, and watch the burn rate alert go from pending to firing, then arrive in Mailpit. Turn it off and watch the alert resolve.

Done when: the alert fires during the fault and resolves after it, and the message shows up only in the local inbox.

## M8: Canary releases with Argo Rollouts

**Goal:** a bad release rolls itself back.

Tasks:
- [ ] Install Argo Rollouts and the `kubectl argo rollouts` plugin.
- [ ] In the library chart, set `rollout.enabled: true` for `order-service`. It now renders a `Rollout` instead of a `Deployment`.
- [ ] Canary steps, for example: 20% weight, pause, analysis, 50%, pause, analysis, 100%.
- [ ] `AnalysisTemplate` with the Prometheus provider: error ratio of the canary pods (filter by the label Argo Rollouts adds to canary pods; see the analysis docs). Fail if it is above a limit you choose.
- [ ] Without a traffic router, weight is set by the number of pods. Optional: the Gateway API traffic router plugin for exact weights.

How to test:
1. Release a good version through the normal tag bump PR. Watch it reach 100%:
   ```bash
   kubectl argo rollouts get rollout order-service -n dev --watch
   ```
2. Release a bad version (fault switch on, or an image that returns errors) under k6 load. Watch the analysis fail and the rollout abort back to the stable version.
3. Note the time from "canary started" to "rollback done".

Done when: the bad release is rolled back with no manual action, and the stable version keeps serving the whole time.

## M9: Scaling, load tests and chaos

**Goal:** the system scales on real signals and survives planned failures. Every experiment is written up.

Tasks:
- [ ] Install KEDA. `ScaledObject` for `search-indexer` (Kafka lag of consumer group `search-indexer` on `orders.events`, max replicas = number of partitions) and for `notification-worker` (queue length on `notifications.email` and `invoices.generate`, min replicas 0).
- [ ] HPA on CPU for `order-service`.
- [ ] k6 scripts in `loadtest/`: a steady load and a spike, with thresholds on error rate and p95 latency. Each request uses a new `Idempotency-Key`.
- [ ] Install Chaos Mesh with the container runtime and socket settings for kind (see its install docs).
- [ ] Experiments in `chaos/`, each with a written hypothesis before you run it:
  1. **Pod kill:** kill 1 `order-service` pod under load. Hypothesis: the error rate stays within the SLO.
  2. **Network delay:** add delay between `payment-service` and its database. Hypothesis: latency rises, alerts fire, no payment is charged twice.
  3. **Kafka broker kill:** stop the broker under load. Hypothesis: orders are still accepted (events wait in the outbox), and after the broker returns, every order completes with no lost or duplicate events.
  4. Optional: stop a kind worker node container (`docker stop orderflow-worker2`) and watch pods move.
- [ ] After each experiment, write an incident write-up in `chaos/incidents/` using the template below.

How to test:
- Run the spike load. Watch `order-service` pods and worker replicas go up, then back down after the load ends.
- For each experiment, compare the result with the hypothesis. A failed hypothesis is a good result: it found a weakness. Fix it or record it.

Done when: KEDA and HPA scaling is visible on dashboards, 3 experiments have write-ups, and the outbox experiment shows 0 lost and 0 duplicate events (checked with a reconciliation query, not by eye).

### Incident write-up template

```markdown
# Incident: <short name>

Date: <yyyy-mm-dd>
Experiment: <file in chaos/>
Hypothesis: <what you expected>

## Timeline

|---|---|

## Impact

## Cause

## Detection

## Fix

| Action | Why |
|---|---|
```

## Showcase demo

Practise this until you can run it in about 5 minutes.

1. **Bad release, automatic rollback.**
   - Show Grafana with k6 load running and the error rate flat.
   - Merge a tag bump PR for a broken version of `order-service`.
   - Show Argo CD syncing, then `kubectl argo rollouts get rollout order-service -n dev --watch`: canary starts, analysis fails, rollout aborts.
   - Show the error rate in Grafana: a small bump, then back to normal. No manual action.
2. **From alert to the exact log line.**
   - Turn on network delay to `payment-service` with Chaos Mesh.
   - Show the latency burn rate alert arriving in Mailpit.
   - Open the latency panel, click an exemplar dot, land on the slow trace in Jaeger, and see the long `payment-service` span.
   - Click "logs for this span" and land on the log lines in Loki with the same `trace_id`.

## Evidence to collect

Only numbers you measured yourself, with the date and the setup (machine, replicas, load) written next to them:

- p50 and p95 latency of `POST /api/orders` at normal and peak k6 load.
- Error rate during each chaos experiment.
- Time from a bad release starting to rollback done.
- Time for the burn rate alert to fire after a fault starts.
- Lost and duplicate event counts after the Kafka broker kill (target: 0 and 0, proven by the reconciliation query).
- Max replicas reached by KEDA and HPA during the spike test.
- Screenshots: Argo CD tree, a full order trace in Jaeger, the RED dashboard during a chaos test, the alert in Mailpit.
