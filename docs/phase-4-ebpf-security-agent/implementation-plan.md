# Phase 4 Implementation Plan

9 milestones, M0 to M8. Finish each one, including its test, before you start the next. Read [architecture.md](architecture.md) first.

The code snippets here are short sketches to show the idea. They are not complete or tested. Check names and fields against your own kernel and library versions.

---

## M0: Environment check and toolchain

**Goal:** Know that your kernel can run what you will build, and have all tools installed.

kind nodes are Docker containers. They do **not** have their own kernel; they use the kernel of the machine (or VM) that runs Docker. So you check that kernel.

**Tasks**

- [ ] Check the kernel version. The ring buffer needs Linux 5.8 or newer.
- [ ] Check that BTF exists (needed for CO-RE).
- [ ] Check that cgroup v2 is used.
- [ ] Check the same 3 things from inside a kind node, to be sure they match.
- [ ] If any check fails on WSL2, create an Ubuntu virtual machine (current LTS) and run Docker, kind and this phase inside it. Do not spend days trying to rebuild the WSL2 kernel.
- [ ] Install the toolchain: `clang`, `llvm`, `libbpf` headers (`libbpf-dev` on Ubuntu), `bpftool`, Go, `make`. On Ubuntu, `bpftool` comes with the `linux-tools` packages for your kernel. If there is no package for your kernel (common on WSL2), build `bpftool` from its GitHub repository.
- [ ] Generate `vmlinux.h`.
- [ ] Write your environment choice (WSL2 or VM) and the reason in the decision log in [`PLAN.md`](../../PLAN.md).

**How to test**

```bash
uname -r                              # kernel version, needs 5.8 or newer
ls -l /sys/kernel/btf/vmlinux         # must exist
stat -fc %T /sys/fs/cgroup            # must print: cgroup2fs

kind get nodes                        # list your kind node names
docker exec -it <node-name> uname -r  # must print the same kernel version

bpftool btf dump file /sys/kernel/btf/vmlinux format c > vmlinux.h
wc -l vmlinux.h                       # a very large file means it worked
```

**Done when:** all checks pass, `vmlinux.h` exists, and the decision is in `PLAN.md`.

## M1: First eBPF program with a Go loader

**Goal:** Load 1 tiny eBPF program from Go and see it run. Learn the build loop before writing real logic.

**Tasks**

- [ ] Create `security/runtime-sentinel/` with a Go module.
- [ ] Put `vmlinux.h` in `security/runtime-sentinel/bpf/headers/`.
- [ ] Write a C program on tracepoint `sched/sched_process_exec` that only calls `bpf_printk("exec")`.
- [ ] Add a `//go:generate` line for `bpf2go` and run `go generate`.
- [ ] Write `main.go` that loads the program, attaches it, and waits for Ctrl+C.
- [ ] Break the program on purpose (for example read memory without a check) to see a verifier error. Fix it.

**Sketch (Go)**

```go
//go:generate go run github.com/cilium/ebpf/cmd/bpf2go -tags linux exec ./bpf/exec.bpf.c -- -I./bpf/headers

func main() {
    var objs execObjects
    if err := loadExecObjects(&objs, nil); err != nil {
        log.Fatalf("load eBPF objects: %v", err)
    }
    defer objs.Close()

    tp, err := link.Tracepoint("sched", "sched_process_exec", objs.HandleExec, nil)
    if err != nil {
        log.Fatalf("attach tracepoint: %v", err)
    }
    defer tp.Close()

    // wait for Ctrl+C
}
```

The names `execObjects`, `loadExecObjects` and `HandleExec` are generated by `bpf2go` from the first argument (`exec`) and your C function name. Yours may differ.

**How to test**

```bash
go generate ./...
go build -o sentinel .
sudo ./sentinel &
sudo cat /sys/kernel/tracing/trace_pipe   # run "ls" in another terminal; you should see "exec" lines
sudo bpftool prog list                    # your program should be in the list
```

**Done when:** you see output for each new process, and you understand the cycle: edit C, `go generate`, build, run.

## M2: Trace process starts (exec)

**Goal:** Send real exec events (pid, parent pid, command, path, cgroup id) to the Go agent through a ring buffer.

**Tasks**

- [ ] Read the tracepoint format: `sudo cat /sys/kernel/tracing/events/sched/sched_process_exec/format`.
- [ ] Define an event struct and a ring buffer map in C.
- [ ] Fill the struct and submit it.
- [ ] In Go, read the ring buffer and print each event as JSON.
- [ ] Add a counter for "ring buffer full" so drops are never hidden.

**Sketch (C)**

```c
//go:build ignore
#include "vmlinux.h"
#include <bpf/bpf_helpers.h>
#include <bpf/bpf_core_read.h>

char LICENSE[] SEC("license") = "GPL";

struct exec_event {
    u64 cgroup_id;
    u32 pid;
    u32 ppid;
    char comm[16];
    char path[128];
};

struct {
    __uint(type, BPF_MAP_TYPE_RINGBUF);
    __uint(max_entries, 256 * 1024);
} events SEC(".maps");

SEC("tracepoint/sched/sched_process_exec")
int handle_exec(struct trace_event_raw_sched_process_exec *ctx)
{
    struct exec_event *e = bpf_ringbuf_reserve(&events, sizeof(*e), 0);
    if (!e)
        return 0; /* buffer full: increase a drop counter here */

    struct task_struct *task = (struct task_struct *)bpf_get_current_task();
    e->pid = bpf_get_current_pid_tgid() >> 32;
    e->ppid = BPF_CORE_READ(task, real_parent, tgid);
    e->cgroup_id = bpf_get_current_cgroup_id();
    bpf_get_current_comm(&e->comm, sizeof(e->comm));

    unsigned int off = ctx->__data_loc_filename & 0xFFFF;
    bpf_probe_read_kernel_str(&e->path, sizeof(e->path), (void *)ctx + off);

    bpf_ringbuf_submit(e, 0);
    return 0;
}
```

**Sketch (Go, reading)**

```go
rd, err := ringbuf.NewReader(objs.Events)
if err != nil {
    log.Fatalf("open ring buffer: %v", err)
}
defer rd.Close()

for {
    record, err := rd.Read()
    if err != nil {
        log.Printf("read ring buffer: %v", err)
        return
    }
    var e execExecEvent // type generated by bpf2go with the -type flag
    if err := binary.Read(bytes.NewReader(record.RawSample), binary.LittleEndian, &e); err != nil {
        log.Printf("decode event: %v", err)
        continue
    }
    // print as JSON
}
```

**How to test**

```bash
sudo ./sentinel | head
# in another terminal:
ls /tmp
bash -c "echo hello"
```

You should see events for `ls`, `bash` and `echo` with correct pids and paths.

**Done when:** every new process shows up as a JSON event with pid, ppid, comm, path and cgroup id.

## M3: Trace sensitive file opens

**Goal:** Catch opens of sensitive files, and **only** those, so the event volume stays small.

**Tasks**

- [ ] Read the format: `sudo cat /sys/kernel/tracing/events/syscalls/sys_enter_openat/format`. The file name is a user space pointer in `args[1]`.
- [ ] Copy the path with `bpf_probe_read_user_str`.
- [ ] Compare it with the short prefix list from [architecture.md](architecture.md#21-ebpf-programs-kernel-side-c). Use a small, bounded loop so the verifier accepts it.
- [ ] Submit only matches. Count all opens and matched opens in a map, so you can show how much the filter saves.
- [ ] Write down the known gap: `open` and `openat2` are not traced.

**Sketch (C, prefix check)**

```c
static __always_inline bool has_prefix(const char *path, const char *prefix, int len)
{
    for (int i = 0; i < len && i < 64; i++) {
        if (path[i] != prefix[i])
            return false;
    }
    return true;
}
```

**How to test**

```bash
sudo ./sentinel &
sudo cat /etc/shadow > /dev/null     # should produce 1 event
cat /etc/hostname                    # should produce no event
```

**Done when:** sensitive opens produce events, normal opens do not, and you can show the count of all opens next to the count of sent events.

## M4: Trace outbound TCP connections

**Goal:** Catch every new outbound TCP connection with source and destination address and port.

**Tasks**

- [ ] Read the format: `sudo cat /sys/kernel/tracing/events/sock/inet_sock_set_state/format`.
- [ ] Attach to tracepoint `sock/inet_sock_set_state`.
- [ ] Keep only events where `protocol` is TCP and `newstate` is `TCP_SYN_SENT` (the client is starting a connection). Check the numeric value of `TCP_SYN_SENT` in your `vmlinux.h` or in the kernel's `tcp_states.h`.
- [ ] Handle both `AF_INET` (IPv4, `saddr` and `daddr`) and `AF_INET6` (IPv6, `saddr_v6` and `daddr_v6`).
- [ ] Check in the format file whether ports are in network or host byte order, and convert in Go if needed.
- [ ] In Go, turn the address bytes into normal IP strings.

**How to test**

```bash
sudo ./sentinel &
curl -m 3 http://203.0.113.10/    # TEST-NET-3: a documentation range, nothing answers
curl -m 3 http://localhost:8080/  # if something listens there
```

`203.0.113.0/24` is reserved for documentation, so the connection attempt is harmless and goes nowhere. You should still see a `tcp_connect` event with `dst_ip` 203.0.113.10 and `dst_port` 80, because the event fires when the connection **starts**.

**Done when:** each `curl` produces exactly 1 `tcp_connect` event with correct addresses and ports.

## M5: Add pod information (enrichment)

**Goal:** Turn "cgroup id 12345" into "pod `order-service-7c9d8-abcde` in namespace `dev`".

**Tasks**

- [ ] Build the cgroup table: walk `/sys/fs/cgroup`, read each folder's inode number (that is the cgroup id), and pull the 64 character container id out of the folder name.
- [ ] Watch pods on this node with client-go (an informer with field selector `spec.nodeName=<NODE_NAME>`). For each pod, read `status.containerStatuses[].containerID` (it looks like `containerd://<id>`).
- [ ] Join both: cgroup id -> container id -> pod name, namespace, container name, labels.
- [ ] Refresh the cgroup table when a new pod starts (a new container means a new cgroup folder).
- [ ] If there is no match, send the event with `k8s: null` and increase an `enrichment_miss` counter.
- [ ] Create a ServiceAccount, ClusterRole (`get`, `list`, `watch` on `pods` only) and ClusterRoleBinding.

**How to test**

```bash
kubectl run enrich-test --image=busybox --restart=Never -- sh -c "sleep 3600"
kubectl get pod enrich-test -o jsonpath='{.status.containerStatuses[0].containerID}'
kubectl exec enrich-test -- ls /
```

The `exec` event for `ls` must show `pod: enrich-test` and the container id must match the one printed by `kubectl`.

**Done when:** events from pods carry the right pod, namespace, container and labels, and you can explain how the mapping works without notes.

## M6: DaemonSet and Kafka

**Goal:** Run the agent on every node as a DaemonSet and send events to Kafka topic `security.events`.

**Tasks**

- [ ] Add a Kafka producer to the agent (for example `franz-go`). Batch events. Set a send timeout and a retry limit. Count send errors on `/metrics`.
- [ ] Use the pod name as the message key (node name when `k8s` is `null`).
- [ ] Create topic `security.events` the same way Phase 2 creates topics (for example a Strimzi `KafkaTopic`). Choose a short retention (for example 1 day), since OpenSearch keeps the long copy.
- [ ] Write a multi-stage Dockerfile: build stage with clang and Go, small runtime image with only the binary.
- [ ] Load the image into kind (`kind load docker-image`).
- [ ] Write the DaemonSet with `NODE_NAME` from the Downward API, `hostPID: true`, and read-only mounts of `/sys/fs/cgroup` and `/sys/kernel/btf`.
- [ ] Start with `privileged: true`. When it works, remove it and add only `CAP_BPF` and `CAP_PERFMON` (and `CAP_SYS_RESOURCE` only if it fails without it). Record what failed without each capability.
- [ ] Add a Helm chart and an Argo CD Application for the agent, like the other services in Phase 2.
- [ ] Expose `/metrics` and add a Prometheus scrape config or ServiceMonitor.

**How to test**

```bash
kubectl get daemonset -n security runtime-sentinel   # DESIRED and READY equal the node count
kubectl logs -n security -l app.kubernetes.io/name=runtime-sentinel --tail=20

# read a few messages from Kafka (run inside a Kafka broker pod)
bin/kafka-console-consumer.sh --bootstrap-server localhost:29092 \
  --topic security.events --from-beginning --max-messages 5
```

**Done when:** 1 agent pod runs on each node, events arrive in `security.events`, the agent runs without `privileged: true`, and the capability findings are written in `security/runtime-sentinel/README.md`.

## M7: detection-service, OpenSearch and alerts

**Goal:** Turn raw events into stored data and real alerts.

**Tasks**

- [ ] Create `services/detection-service/` (Python, `uv`, `ruff`, `pytest`) following the [conventions](../common/07-conventions.md).
- [ ] Consume `security.events` with `confluent-kafka` (group `detection-service`). Commit offsets **after** the OpenSearch write succeeds (at least once delivery).
- [ ] Load `rules.yaml` and write a small matcher (equals, in list, not in list, IP in CIDR).
- [ ] Write unit tests: for each rule, 1 event that must match and 1 that must not.
- [ ] Create an index template for `security-events-*` with field types.
- [ ] Create the ISM policy (delete after 7 days).
- [ ] Bulk write every event to `security-events-YYYY.MM.DD`, with the document id set to `event_id` so a repeated event does not make a copy.
- [ ] For each match, `POST` an alert to Alertmanager `/api/v2/alerts` with `httpx` (timeout set) and `tenacity` (retry limit set).
- [ ] Expose `/metrics`: events processed, alerts per rule, write errors.
- [ ] Deploy it with Helm and Argo CD.

**Sketch (ISM policy)**

```json
PUT _plugins/_ism/policies/security-events-retention
{
  "policy": {
    "description": "Delete security events after 7 days",
    "default_state": "hot",
    "states": [
      {
        "name": "hot",
        "actions": [],
        "transitions": [{ "state_name": "delete", "conditions": { "min_index_age": "7d" } }]
      },
      {
        "name": "delete",
        "actions": [{ "delete": {} }],
        "transitions": []
      }
    ],
    "ism_template": { "index_patterns": ["security-events-*"], "priority": 100 }
  }
}
```

**How to test**

```bash
uv run pytest                                          # all rule tests pass

curl -s "localhost:9200/_cat/indices/security-events-*?v"     # daily index exists, doc count grows
curl -s "localhost:9200/_plugins/_ism/explain/security-events-*"  # policy is attached

kubectl exec enrich-test -- sh -c "echo test"          # should NOT alert (not a web container)
```

To test that deletion really works without waiting 7 days, attach a copy of the policy with a short `min_index_age` to a test index pattern, and check that the test index disappears.

**Done when:** events are searchable in OpenSearch, the ISM policy is attached, all rule tests pass, and a matching event creates an alert you can see in Alertmanager.

## Showcase demo

This is the 2 minute demo for the interview. Run it only on your own cluster.

**Setup (before the demo)**

Deploy a small demo pod that looks like a web container and has `sh` and `curl`:

```bash
kubectl run demo-web -n dev --image=curlimages/curl \
  --labels="app.kubernetes.io/name=demo-web,app.kubernetes.io/component=api" \
  --command -- sleep infinity
```

Open the Grafana security dashboard and the Alertmanager UI side by side.

**Steps**

1. Show the dashboard: events flowing, 0 alerts.
2. Open a shell in the "web" pod:
   ```bash
   kubectl exec -it -n dev demo-web -- sh
   ```
   Alert 1 fires: `shell-in-web-container`, pod `demo-web`.
3. From that shell, connect to an address that is not on the allowlist (a documentation range, nothing answers):
   ```bash
   curl -m 3 http://203.0.113.10/
   ```
   Alert 2 fires: `unexpected-outbound-connection`, with `dst 203.0.113.10:80` and pod `demo-web`.
4. Read the pod's Kubernetes token:
   ```bash
   cat /var/run/secrets/kubernetes.io/serviceaccount/token > /dev/null
   ```
   Alert 3 fires: `sensitive-file-read`.
5. Open OpenSearch (or the Grafana events table) and show the full event chain for `demo-web`, in order.
6. Show the overhead table and say what it costs to run.

Measure the time from each command to its alert during rehearsal, and quote only that measured time.
