1. How to use this guide

  1. Learn the pitch. Say it out loud until you can do it in under 2 minutes without reading.
  2. Practice the whiteboard walkthrough. Draw the system from memory and explain 1 order end to end.
  3. Use the question bank to test yourself. Answers are hidden. Read the question, answer out loud, then open the answer and compare. Tick "Practiced" only when you can answer without looking.
  4. Go from easy to hard. Filter by Basic first, then Medium, then Hard.
  5. Do the failure drills. A senior interviewer will almost always ask "what happens when this breaks?". These drills prepare you for that.
  6. Rehearse the live demo with a timer, and prepare the backup plan.

The model answers are here to check your thinking. Put them in your own words. An answer that sounds memorised is weaker than a simple answer you clearly understand.

Honesty rule Only say "I built" for parts you have actually built and run. If a phase is not done yet, say: "I have not built that part yet. Here is how I would approach it." That is a good answer. A senior person notices very quickly when someone describes things they never ran. "I don't know, but this is how I would find out" is also a good answer. Never invent numbers: every [measured number] in this guide must come from your own tests, or the sentence must be removed.

2. The 2 minute pitch

"OrderFlow is a small online ordering system I built to learn the full stack that real production systems use. A customer places an order, the system reserves the stock, takes a payment and confirms the order. If any step fails, it undoes the earlier steps.

The interesting part is not the features. It is keeping the system correct when things break. The services do not call each other in a chain. Each service saves its change and an event in its own PostgreSQL database in 1 transaction, using the outbox pattern, and Debezium publishes those events to Kafka. The order-service runs a saga: if the payment fails, it asks inventory to release the stock. Every consumer is idempotent, so a duplicate event does nothing. Redis reserves stock with a Lua script, so 2 customers cannot buy the last item. RabbitMQ handles jobs like emails and PDF invoices, and OpenSearch makes orders searchable.

Then I ship it the way a real team does. It runs on Kubernetes with a Helm chart, Argo CD deploys it from Git, and canary releases roll back by themselves when the error rate goes up. Prometheus, Grafana, Loki and Jaeger show metrics, logs and traces for every request.

I also extended the platform: a Go operator that creates a full app environment from 1 YAML file, an eBPF agent that watches process, file and network activity on each node, and an AWS version built with Terraform behind CloudFront and WAF.

In my chaos tests I placed [measured number] orders while killing services, and found [measured number] lost or duplicated payments. The p99 latency to place an order was [measured number] ms."

Before you use it Remove every sentence about a phase you have not finished. Replace the placeholders with your own measured results. If you have no measurement yet, say "I have not measured that yet" rather than guessing.

3. Whiteboard walkthrough: 1 order, end to end

Draw from left to right and keep everything on 1 board. Talk while you draw. After each step, pause briefly so the interviewer can stop you and ask a question.

  1. Draw the customer and the load balancer. "Every request enters through 1 door: nginx locally, Gateway API on Kubernetes, an ALB on AWS."
  2. Draw 3 boxes: order-service, inventory-service, payment-service. Give each its own database. "Each service owns its data. No service reads another service's tables. They talk through events."
  3. Place an order. "The client sends POST /api/orders with an Idempotency-Key. order-service saves the order as PENDING and writes an OrderCreated row into its outbox table, in the same transaction. It returns 202 Accepted straight away."
  4. Draw Debezium and Kafka. "Debezium reads the outbox from the Postgres write-ahead log and publishes OrderCreated to the orders.events topic, using order_id as the key so all events for 1 order stay in order."
  5. Stock. "inventory-service reads OrderCreated. It first checks processed_events, so a duplicate does nothing. A Lua script in Redis checks and reduces the stock in 1 atomic step. Then it saves the reservation and a StockReserved event in 1 transaction."
  6. Payment. "order-service moves the order to STOCK_RESERVED and emits ChargePaymentRequested. payment-service charges the fake provider using the order_id as an idempotency key, then emits PaymentSucceeded."
  7. Confirm. "order-service marks the order CONFIRMED. The receipt email and the invoice are sent as RabbitMQ jobs. notification-worker sends the email to Mailpit and stores the PDF in S3. search-indexer updates OpenSearch."
  8. Draw the failure path in another colour. "If the payment fails, order-service emits ReleaseStockRequested, inventory gives the stock back and emits StockReleased, and the order becomes CANCELLED. That is the compensation step of the saga."
  9. Draw the observation layer on top. "Every service sends traces, metrics and logs through the OpenTelemetry Collector to Jaeger, Prometheus and Loki, and Grafana shows them together. The trace context travels in Kafka and RabbitMQ headers, so 1 order is 1 trace."
  10. Draw the platform at the bottom. "Code goes from Git through GitHub Actions to an image. Argo CD deploys the Helm chart to Kubernetes with a canary. The operator creates environments, the eBPF agent watches every node, and on AWS the same services run on ECS Fargate, built with Terraform."

Tip: when you finish, ask "Which part would you like me to go deeper on?". The interviewer then chooses the topic, and you get to show depth where it matters to them.

5. Failure scenario drills

For each drill, answer out loud in 4 parts: what happens, how you detect it, what you do, and how the design limits the damage. Then open it to compare.

Drill 1: Kafka is down for 10 minutes

What happens

Services keep saving to their own databases and outbox tables. The API still accepts orders (202), but they stay PENDING. Debezium cannot publish and keeps retrying. Nothing is lost, because the events are safe in Postgres.

How you detect it

Broker down alert, Debezium connector status in Kafka Connect, a metric for the age of PENDING orders, and growing replication slot lag.

What you do

Bring the broker back. If the connector task is FAILED, restart it. Debezium continues from its last committed position. Watch the lag go down, then check for orders stuck in PENDING.

How the design limits the damage

The outbox keeps every event durable in Postgres. Idempotent consumers handle the duplicates Debezium may send after it restarts.

Drill 2: Debezium stops for several hours

What happens

The replication slot keeps WAL, so the Postgres disk grows. Events are delayed and orders stay PENDING.

How you detect it

Retained WAL per slot from pg_replication_slots, a disk usage alert, the connector status, and the PENDING age metric.

What you do

Fix and restart the connector. If max_slot_wal_keep_size was reached and the slot was invalidated, take a new snapshot and re-publish the events from the kept outbox rows for the gap.

How the design limits the damage

The WAL limit protects the database disk, early alerts give time to act, and outbox rows are kept for a while so events can be re-published.

Drill 3: Redis loses all its data

What happens

Stock counters, holds, caches, idempotency keys and rate limit counters are gone.

How you detect it

Redis restart event, a spike in cache misses, inventory errors about missing stock keys.

What you do

inventory-service reports not ready and rebuilds stock:* and holds from Postgres (stock minus active reservations). Then it reports ready again. Caches refill by themselves.

How the design limits the damage

Postgres is the source of truth. The unique constraint on the idempotency key in Postgres still stops duplicate orders.

Drill 4: The payment provider times out, but it actually charged the card

What happens

payment-service does not know if the charge happened. A blind retry could charge twice.

How you detect it

Timeout errors on provider calls, and payments stuck in PENDING.

What you do

Never treat a timeout as a failure. Retry with the same idempotency key (the order_id) or ask the provider for the status. The provider returns the original result. A reconciliation job compares provider records with payments_db.

How the design limits the damage

The PENDING row is saved before the call, the provider gets an idempotency key, and recovery is automatic.

Drill 5: A bad release reaches production

What happens

Error rate or latency goes up on the new version.

How you detect it

The Argo Rollouts analysis (Prometheus query on the canary's 5xx ratio) fails, and SLO burn rate alerts fire.

What you do

Rollouts aborts by itself and sends traffic back to the stable version. If the release was already fully rolled out, revert the image tag commit in Git and Argo CD syncs. Write a postmortem.

How the design limits the damage

The canary limits how many users see the bug. Expand-and-contract migrations mean the old version still works with the database.

Drill 6: The Postgres disk is full

What happens

Writes fail. Services return errors and readiness should fail.

How you detect it

A disk usage alert well before 100% (for example at 80%), and a jump in database errors.

What you do

Find the cause: WAL held by a slot, table bloat, or logs. Free space or grow the volume (if the storage class allows it), then fix the root cause.

How the design limits the damage

Early alerts, a WAL limit for slots, and outbox cleanup.

Drill 7: Consumer lag keeps growing

What happens

Events are processed late. For the saga, orders take longer to confirm. For search, results are old.

How you detect it

A consumer lag metric per group and per partition.

What you do

1 partition only: look for a poison message and move it to the DLQ. All partitions: check traces for a slow dependency, batch the work, check for rebalance loops, and scale up to the number of partitions.

How the design limits the damage

KEDA scales on lag, retries are limited, and dead letter topics stop 1 bad message from blocking a partition.

Drill 8: A Kubernetes node dies

What happens

Pods on the node stop responding. After the default toleration (300 seconds for not-ready or unreachable nodes) they are rescheduled on other nodes. CloudNativePG fails over Postgres if the primary was on that node.

How you detect it

Node NotReady, pod restarts, a short dip in the success rate.

What you do

Mostly automatic. Check that every service has at least 2 replicas spread across nodes.

How the design limits the damage

Multiple replicas with topology spread, readiness probes, PDBs, and operators that handle failover.

Drill 9: The webhook's TLS certificate expires

What happens

The API server cannot call the webhook. With failurePolicy: Fail, creating or updating matching objects fails.

How you detect it

API errors that mention an expired x509 certificate, a cert-manager Certificate that is not Ready, and an alert on the certificate expiry metric.

What you do

Fix the cert-manager issuer or certificate and check that the CA is injected into the webhook configuration.

How the design limits the damage

cert-manager renews certificates well before they expire. kube-system and the operator's namespace are excluded, so the cluster keeps working.

Drill 10: The eBPF agent floods Kafka

What happens

A noisy event, for example file opens in a busy container, creates a huge volume. Kafka disk fills, detection lags, and node CPU rises.

How you detect it

Events per second per node, ring buffer drop counters, bytes into security.events, and detection-service lag.

What you do

Tighten the filters in the kernel, rate limit per pod, batch and compress in the producer, and set topic retention.

How the design limits the damage

Filtering happens in the kernel, the ring buffer is bounded (it drops instead of blocking), and the DaemonSet has resource limits.

Drill 11: The Terraform state is locked, or the state file is broken

What happens

"Error acquiring the state lock" because an earlier apply crashed. Or the state file was damaged or lost.

How you detect it

terraform plan or apply fails.

What you do

Locked: make sure nobody is running Terraform, then terraform force-unlock LOCK_ID. Broken: restore an earlier version from the versioned S3 bucket, run plan to see the drift, and use import blocks for resources missing from state.

How the design limits the damage

A versioned, encrypted state bucket, use_lockfile locking, and CI as the only place that runs apply.

Drill 12: A secret was committed to Git

What happens

Anyone with access to the repository, now or later, can use it.

How you detect it

Secret scanning in CI or GitHub push protection, or someone sees it.

What you do

Treat it as leaked. Rotate it at once and revoke the old one. Report it the same day. Then remove it from the history. Rotation is the real fix; cleaning history alone is not.

How the design limits the damage

.env is git-ignored, secrets come from env vars and a secret manager, and scanning runs on every pull request.

Drill 13: A poison message blocks a consumer

What happens

1 message always fails, so the consumer retries forever and its partition stops moving.

How you detect it

Lag on 1 partition only, and the same error repeated in the logs.

What you do

After the retry limit the message goes to the .dlq topic. An alert fires. Fix the bug or the data, then replay the message from the DLQ.

How the design limits the damage

Limited retries and dead letter topics.

Drill 14: OpenSearch is down

What happens

Search returns errors. Placing orders keeps working, because search is not on the critical path. search-indexer stops committing offsets, so its events wait in Kafka.

How you detect it

Cluster health red, search errors, search-indexer lag.

What you do

Recover the cluster. The indexer catches up from its offsets. If the index is damaged, rebuild it into a new index and switch the alias.

How the design limits the damage

Search is separate from the order flow, indexing is idempotent, and the alias allows a rebuild with no downtime.

Drill 15: notification-worker crashes in the middle of a job

What happens

The job was not acked, so RabbitMQ redelivers it to another worker.

How you detect it

Pod restarts and redelivery counts.

What you do

Nothing special. The email is skipped if notified:{order_id} is set. The invoice overwrites the same S3 key.

How the design limits the damage

Manual acks, idempotent jobs and dead letter queues.

Drill 16: A sudden 10 times traffic spike

What happens

Latency rises, database connections fill up, and queues and lag grow.

How you detect it

Request rate, saturation metrics, and the SLO burn rate.

What you do

Autoscaling adds pods. Rate limits return 429 to protect the core. Watch database connections and the pooler.

How the design limits the damage

Async processing absorbs bursts, the Redis Lua script keeps stock correct under contention, and rate limits protect the system.

Backup plan if the demo breaks
  • Record a video of every step the day before and keep it open in another window.
  • Keep screenshots of the key screens (Grafana, Jaeger, Argo Rollouts, Kafka UI).
  • Pre-pull every image so the demo does not need the internet. Have a reset script that puts everything back to a clean state.
  • Start the whole system 1 hour before, and check every step once.
  • If something fails live, stay calm: say what you expected, then show how you would debug it with the logs and traces. That is a good signal in itself. Then switch to the video.

7. Good questions to ask the interviewer

  1. What problem does the product I would work on solve, and who uses it?
  2. Which parts of the stack are already decided, and which are still open (for example ECS or Kubernetes)?
  3. What traffic and data size do you expect in the first 6 months?
  4. What does "done" look like for the first release?
  5. How will we deploy? Who owns the infrastructure, and is there a staging environment?
  6. Is there a cloud budget limit I should design for?
  7. What reliability does the product need? Are there SLOs or customer commitments?
  8. Will the system handle personal or sensitive data? Are there compliance rules?
  9. How are decisions recorded, and who reviews code?
  10. Which part would you want me to own first?
  11. In 3 months, what would make you say putting me on this project was the right choice?
